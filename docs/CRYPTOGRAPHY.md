# SecureVault — Cryptographic Architecture

## 1. Cryptographic Principles & Standards

SecureVault strictly adheres to modern, vetted cryptographic standards:
- **Standardized Primitives Only**: Every algorithm and mode is standardized by bodies such as IETF and NIST. No custom ciphers or non-standard compositions.
- **KDF vs. Encryption Separation**: We strictly distinguish between **Password Key Derivation Functions (KDF)** (which transform variable-entropy human passwords into pseudo-random keys) and **Symmetric Authenticated Encryption** (which protects confidentiality and integrity of messages using uniform random keys).
- **Authenticated Encryption with Associated Data (AEAD)**: All ciphertexts include cryptographically bound authentication tags verifying integrity and authenticity prior to decryption.

## 3. Key Hierarchy & Envelope Encryption

SecureVault utilizes a two-tier key hierarchy:

```
[User Master Password] + [Vault Salt (16B)] + [Argon2id Parameters]
                           │
                           ▼ (Argon2id KDF)
            [Key Encryption Key (KEK)] (256-bit)
                           │
                           ▼ (AES-256-GCM Decrypt with AAD_DEK)
       [Wrapped DEK (Ciphertext 32B + Tag 16B)] (Header offsets 0x32 - 0x61)
                           │
                           ▼
            [Data Encryption Key (DEK)] (256-bit)
                           │
                           ▼ (AES-256-GCM Decrypt with AAD_PAYLOAD)
            [Vault Payload Ciphertext] (Starting at offset 0x86)
                           │
                           ▼
          [Decrypted Plaintext Vault JSON]
```

### 3.1 Benefits of Two-Tier Architecture (KEK / DEK)
1. **Instant, Atomic Master Password Changes**: When the user changes their master password, only the 32-byte DEK is re-wrapped with a newly derived KEK and new salt. The large vault payload does not need to be re-encrypted, eliminating the risk of partial corruption during password rotation.
2. **Key Independence**: The Data Encryption Key (DEK) is a uniformly distributed 256-bit random key generated by the OS CSPRNG, completely independent of human password biases.

---

## 4. Master Password Handling & Memory Hygiene

1. **Transient Ingestion**:
   - Master password text captured in the PySide6 UI is converted directly to UTF-8 encoded bytes.
   - It is passed directly into the Argon2id key derivation function.
2. **Best-Effort Memory Hygiene in Python**:
   - Variables referencing the master password or raw key buffers are reassigned to `None` as soon as key derivation completes.
   - Where mutable byte buffers (`bytearray`) are used, they are overwritten in-place with zeros (`b'\x00'`) before being dereferenced.
3. **Explicit Python Memory Limitations**:
   - Python is a high-level language with automated garbage collection, string interning, and immutable string objects.
   - **Important Limitation**: Overwriting mutable buffers and invoking `gc.collect()` are best-effort hygiene measures; they **cannot guarantee physical memory erasure** at the operating system or hardware level. Unallocated heap memory, OS paging files, or hibernation images may retain transient byte fragments until overwritten by unrelated allocations.
4. **Zero Persistence**:
   - The master password is never stored on disk, never stored in configuration files, and never included in error traces.

## 5. Key Derivation (Argon2id)

SecureVault specifies **Argon2id** (RFC 9106), combining Argon2d (resistance against GPU/ASIC acceleration via memory-hardness) and Argon2i (resistance against side-channel cache timing attacks).

Implemented in `app/crypto/kdf.py` via `argon2-cffi` (`argon2.low_level.hash_secret_raw(..., type=Type.ID)`).

### Production Parameter Specifications:
- **Type**: `Argon2id` (RFC 9106, hybrid mode).
- **Memory Cost (`m`)**: `65,536 KiB` (64 MiB). Requires dedicated RAM per guess, significantly increasing memory cost and substantially impeding parallel attack throughput on GPUs and ASICs.
- **Time Cost (`t`)**: `3` iterations. Provides adequate computation hardness while maintaining unlock latency under ~0.5 seconds on modern desktop CPUs.
- **Parallelism (`p`)**: `4` lanes. Exploits multi-core desktop architectures.
- **Salt Length**: 16 bytes generated via `secrets.token_bytes(16)`. Guarantees uniqueness and renders pre-computed rainbow tables ineffective.
- **Derived Key Length**: Exactly 32 bytes (256-bit KEK).

### Fast Test Parameters vs. Production Defaults
To maintain lightning-fast test execution while never weakening production security:
- `KDFParameters.fast_for_testing()` provides reduced parameters (`m=1024 KiB, t=1, p=1`) strictly for unit tests.
- Production instantiations (`KDFParameters()`) enforce full M0 parameters (`m=65536 KiB, t=3, p=4`) by default.
- Test suites explicitly verify both the fast testing parameters and the full production parameters.

## 6. Authenticated Encryption (AES-256-GCM)

All encryption operations employ **AES-256-GCM (Galois/Counter Mode)**:

### 6.1 Nonce (Initialization Vector) Rules
- **Length**: Exactly 96 bits (12 bytes).
- **Generation**: Generated using `secrets.token_bytes(12)` immediately prior to each encryption.
- **Uniqueness Guarantee**: Under GCM, nonce reuse under the same key completely compromises confidentiality and authenticity. SecureVault generates a fresh CSPRNG nonce for **every write operation**, whether wrapping the DEK or encrypting the payload.

### 6.2 Authentication Tag & Associated Authenticated Data (AAD)
- **Tag Length**: 128 bits (16 bytes).
- **Integrity Verification**: Prior to decrypting any ciphertext block, the Galois Hash authentication tag is verified. If a single bit in the ciphertext, nonce, or associated data is altered, decryption halts and raises an integrity error.
- **Exact AAD Definitions**:
  - **For Wrapped DEK**: `AAD_DEK = file_bytes[0x00 : 0x26]` (38 bytes: `MAGIC` through `SALT`).
  - **For Encrypted Payload**: `AAD_PAYLOAD = file_bytes[0x00 : 0x0A] + file_bytes[0x62 : 0x6A]` (18 bytes: `MAGIC` + `FORMAT_VERSION` + `PAYLOAD_LEN`).
  - *Decoupling*: Excluding salt and KEK parameters from `AAD_PAYLOAD` ensures changing the master password does not invalidate the payload authentication tag.

## 7. Tamper Detection & Wrong-Password Behavior

When a user attempts to unlock a vault:
1. The derived KEK attempts to decrypt the wrapped DEK using `AAD_DEK`.
2. If the user provided the wrong master password, the derived KEK differs mathematically from the creation KEK.
3. Under AES-256-GCM, attempting decryption with an incorrect key causes authentication tag validation to fail.
4. **Indistinguishable Error Response**: The application catches `InvalidTag` (or `DecryptionError`) and surfaces a unified message:
   `"Invalid master password or vault file corrupted."`
   This intentional design prevents adversaries from distinguishing between file tampering, corrupted headers, or incorrect passwords, mitigating oracle attack vectors.

---

## 8. Master Password Change & Key Rotation Flow

When the user changes their master password while the vault is unlocked:
1. Verify the current master password.
2. Receive and validate the new master password.
3. Generate a fresh 16-byte cryptographic salt via `secrets.token_bytes(16)`.
4. Run Argon2id to derive a new 256-bit `KEK_new`.
5. Generate a fresh 12-byte nonce `DEK_NONCE_new`.
6. Construct `AAD_DEK_new` (bytes `0x00` through `0x25` with the new salt).
7. Encrypt the existing active in-memory `DEK` with `KEK_new` using AES-256-GCM and `AAD_DEK_new`.
8. Update the vault header on disk with the new salt, new DEK nonce, new wrapped DEK, and new DEK auth tag.
9. Best-effort overwrite and dereference `KEK_new`.

*Because the DEK and the payload AAD remain unchanged, the vault payload is not re-encrypted, guaranteeing an atomic, instantaneous password rotation.*
